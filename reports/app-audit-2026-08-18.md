# Mohasib application audit

Date: 2026-08-18  
Scope: current local working tree, including uncommitted homepage/SEO changes  
Verdict: **Technical release blockers remediated locally; legal sign-off and migration deployment remain required**

## Remediation update

Implemented after the initial audit:

- **Fixed:** production email-parser dependency advisory. `npm audit --omit=dev` now reports zero vulnerabilities.
- **Fixed:** inbound email now enforces raw-message, attachment-count, per-file, cumulative-size, sender, dossier, and plan-usage limits; skips HTML-to-text conversion; deduplicates attachments; and cleans up failed writes.
- **Fixed:** rate-limit increments now use an atomic, service-role-only Postgres RPC and fail closed when unavailable.
- **Fixed:** receipt/company-document/invoice-PDF buckets and tenant storage policies are defined in ordered migration `086`; receipt files are private and UI access uses five-minute signed URLs.
- **Fixed:** OCR uploads use the account-owner namespace and roll back storage on database failure.
- **Fixed:** the client list reloads and clears when owner/dossier context changes.
- **Fixed:** a baseline enforced Content Security Policy is present.
- **Fixed:** production builds use Webpack because the Next.js 16 Turbopack build stalled in this repository; the Webpack production build completes successfully.
- **Fixed:** focused MIME/deduplication tests were added, and all eight desktop/mobile E2E smoke tests pass.
- **Pending decision:** public CGU/privacy placeholders still require confirmed operational retention periods and a jurisdiction choice. They were intentionally not replaced with invented legal commitments.
- **Remaining low-priority debt:** ESLint still reports 113 pre-existing warnings across the wider application. The tenant-context warning identified as a concrete privacy/correctness risk was fixed.

## Executive summary

The application has a solid baseline: authenticated API routes generally re-check the Supabase session, privileged admin operations use a centralized admin guard, tenant access is reinforced by RLS and permission helpers, OAuth state is signed and time-limited, secrets were not found in tracked source, all 56 unit tests pass, type checking passes, and all 84 ordered migrations validate.

The main release blockers are the inbound-email processing surface and its dependency chain. The endpoint parses attacker-controlled email, processes every supported attachment through OCR, and does not enforce per-message size/count limits or account usage quotas. The same path uses `mailparser`, whose installed transitive dependency tree currently has three high-severity audit findings. There are also reliability gaps in rate limiting, storage provisioning, OCR persistence, client-side data refreshes, legal copy, and test coverage.

## Prioritized findings

### P1 — High: vulnerable production dependency in the inbound-email parser

- Evidence: `package.json:43` allows `mailparser`; the installed tree is `mailparser@3.9.14 -> html-to-text@10.0.0 -> deepmerge-ts@7.1.5`.
- `npm audit --omit=dev` reports three high-severity vulnerabilities for `deepmerge-ts <8.0.0` (GHSA-ggr8-5vv4-36mx, stack exhaustion when merging recursive object graphs).
- Reachability: `src/app/api/email/inbound/route.ts:43` parses externally supplied raw email with `simpleParser(raw)`.
- Impact: crafted input may cause process stack exhaustion or denial of service. Exact exploitability through `mailparser` should be confirmed, but this is a production dependency on an untrusted-input path.
- Recommendation: upgrade or override the chain so `deepmerge-ts >=8`, verify `mailparser` compatibility, add a malicious/oversized MIME regression test, and rerun `npm audit`. Do not apply `npm audit fix --force` without reviewing its proposed `mailparser` downgrade.

### P1 — High: inbound email can bypass OCR quotas and consume unbounded work

- Evidence: `src/app/api/email/inbound/route.ts:19-43` accepts and parses the complete raw message; lines 56-86 iterate over every image/PDF attachment and invoke OCR.
- There is no raw-body limit, attachment-count limit, per-attachment limit, sender throttling, account quota check, or idempotency key.
- The interactive OCR route has a 10 MB file limit and usage accounting (`src/app/api/ocr/route.ts:15-28,54-57,100-103`), but inbound email does not use either control.
- Impact: anyone who learns or guesses a dossier inbox address can repeatedly consume storage, OCR/AI spend, and server time. Retries from the mail worker can multiply work because messages are not deduplicated.
- Recommendation: reject oversized messages before parsing; cap attachment count and cumulative decoded bytes; enforce the same account plan/usage counters as interactive OCR; deduplicate on provider message ID/content hash; rate-limit by dossier and sender; queue OCR with bounded concurrency.

### P2 — Medium: rate limiting is race-prone and relies directly on a forwarded header

- Evidence: `src/lib/rate-limit.ts:121-159` performs a read-modify-write sequence rather than an atomic database increment.
- Parallel requests can read the same attempt count and overwrite each other, allowing bursts beyond configured limits.
- `src/lib/rate-limit.ts:101-105` trusts the first `x-forwarded-for` value. This is safe only if the production edge always overwrites that header; otherwise callers can rotate spoofed values.
- The implementation also fails open when the service-role client is unavailable (`src/lib/rate-limit.ts:114-116`). The health endpoint detects missing configuration, but code-level enforcement remains fail-open.
- Recommendation: move the check/increment/block operation into one transactional Postgres RPC, key expensive authenticated operations by account/user as well as IP, normalize only trusted platform IP headers, and fail closed for authentication and costly public endpoints.

### P2 — Medium: storage setup is not reproducible from migrations

- Evidence: receipt bucket creation and RLS policies are commented out in `supabase/migrations/002_receipts.sql:41-60`; company-document storage setup is also commented out in `supabase/migrations/004_company_documents.sql:26-36`.
- README instructs deployments to run migrations, but a fresh database will still depend on undocumented/manual dashboard state for key document flows.
- Impact: fresh environments can fail uploads, deploy with inconsistent storage access rules, or drift from production without migration history recording the change.
- Recommendation: add idempotent ordered migrations for every required bucket and storage policy, and add a deployment smoke test that exercises upload, signed read, and delete under owner/collaborator/client-portal roles.

### P2 — Medium: OCR persistence can create broken records or orphaned files

- Evidence: `src/app/api/ocr/route.ts:67-71` treats storage upload failure as non-fatal, then inserts a receipt with a null `storage_path` at lines 84-98.
- If the later database insert fails, the successfully uploaded object is not removed.
- The storage path starts with the session user ID (`line 64`), while the receipt is owned by the resolved account owner (`line 87`). With folder-based storage RLS, collaborator uploads may be unreadable by the owner and vice versa.
- Recommendation: make storage failure stop the request; compensate by deleting an uploaded object when database insertion fails; use a consistent tenant storage prefix; test owner and collaborator access explicitly.

### P2 — Medium: client list can retain data from a previous account/dossier context

- Evidence: `src/app/(app)/clients/page.tsx:215-242` closes over `ownerId`, `dossierId`, and `supabase` but memoizes `load` with an empty dependency array.
- ESLint and the React compiler both flag this dependency mismatch.
- Impact: if account/dossier context changes without a full remount, the view can keep querying or displaying the previous context until another remount/refresh. RLS limits unauthorized reads, but stale authorized data is still a privacy and correctness concern.
- Recommendation: include all dependencies or remove the memoization, clear current rows when the scope changes, and add a test that switches dossier/account context in-place.

### P2 — Medium: public legal documents contain unresolved placeholders

- Evidence: `src/app/cgu/page.tsx:107` leaves the post-termination data-access duration unresolved; `src/app/cgu/page.tsx:182-183` leaves jurisdiction unresolved.
- `src/app/confidentialite/page.tsx:128-130,177` leaves retention periods and analytics-cookie disclosure unresolved.
- Impact: users are presented incomplete contractual/privacy terms, and actual retention/cookie practices cannot be verified against the published policy.
- Recommendation: have Moroccan counsel/privacy ownership finalize the terms, verify them against actual deletion/logging/analytics behavior, and block release when `[TODO:` is present in public legal pages.

### P3 — Low: no Content Security Policy

- Evidence: `next.config.js:4-12` sets HSTS, frame, MIME, referrer, and permissions headers, but no `Content-Security-Policy` or report-only policy.
- Impact: an XSS or compromised third-party script would have fewer browser-enforced containment barriers.
- Recommendation: deploy a nonce-based CSP in report-only mode first, collect violations, then enforce it. Include explicit rules for Supabase, Sentry, Sanity, Turnstile, image/media assets, and OAuth integrations.

### P3 — Low: warning debt and coverage are disproportionate to application risk

- Evidence: ESLint reports 116 warnings, including missing hook dependencies, state updates inside effects, components declared during render, image optimization, accessibility, and unused code.
- Repository size: 427 TypeScript/TSX source files, 102 API routes, and 84 migration SQL files, but only 9 unit-test files and one E2E spec containing four scenarios.
- Existing tests do not cover tenant isolation, admin authorization, OAuth callback integrity, public share tokens, inbound email, rate-limit concurrency, storage RLS, payroll, or payment/reconciliation mutation flows.
- Recommendation: promote correctness-oriented hook rules to errors after cleaning the current backlog, and prioritize integration tests around tenant boundaries and money-changing workflows over broad snapshot/UI tests.

## Positive controls observed

- Centralized admin API authorization returns a non-discoverable 404 for non-admins.
- Most sensitive API routes independently authenticate rather than relying only on middleware.
- Permission checks and tenant-scoped RLS are used extensively; later migrations explicitly harden tenant boundaries.
- OAuth state tokens are HMAC-signed, bound to the current user, stored in HttpOnly/SameSite cookies, and expire after ten minutes.
- OAuth tokens are encrypted with AES-256-GCM when stored.
- Public quote/invoice links require a high-entropy response token in addition to the record ID.
- Interactive OCR and bank-import flows apply file-size/type checks.
- Security headers, no-store health checks, audit logging, migration-history validation, and Sentry integration are present.
- No obvious committed credentials or private keys were found.

## Recommended remediation order

1. Fix and regression-test the vulnerable email-parser dependency chain.
2. Bound, deduplicate, quota, and queue inbound-email OCR work.
3. Make storage buckets/policies migration-managed and repair OCR rollback/tenant paths.
4. Replace rate-limit read-modify-write logic with an atomic database operation.
5. Resolve legal-policy placeholders before public release.
6. Fix stale hook dependencies, beginning with tenant/dossier-scoped screens.
7. Make `next build` deterministic and add authorization/tenant-isolation integration tests.
8. Roll out a report-only CSP, then enforce it.

## Limitations

This was a static/local audit. It did not inspect the live Supabase policy catalog, Vercel/Cloudflare configuration, production logs, Sentry issues, actual backup/restore behavior, or a deployed browser session. Those controls should be verified separately before a formal security or compliance attestation.
